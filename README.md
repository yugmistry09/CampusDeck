# CampusDeck

CampusDeck is a **local-first desktop application for students** to manage academic tasks, coursework, subjects, documents, and related files in one place.

It is designed to keep academic work organized by subject while connecting tasks with their relevant documents, due dates, and completion status. Assignments, lab manuals, practicals, solution files, syllabi, notices, and other academic material can be managed without relying on a cloud service.

CampusDeck is **local-first and offline by design**. No account, server, cloud storage, telemetry, or network connection is required for normal operation. Your application data and imported files remain on your own machine.

---

## Features

- Subject-wise organization of academic work and documents
- Central task/to-do list with due dates and completion status
- Assignments, lab manuals, practicals, and general tasks
- Assignment documents linked directly to their corresponding tasks
- Multiple solution/reference files per assignment
- Subject miscellaneous files such as syllabi, notices, marks, and other documents
- Overall task completion/progress tracking
- App-managed local document library
- Manual full backup and restore
- Versioned database migrations
- Offline operation with no cloud dependency
- Safe restore with validation, checksum verification, and rollback protection

---

## Fixed Technology Stack

- **Desktop Runtime**: Electron 33 (Chromium + Node.js)
- **Bundler & Dev Server**: electron-vite (Vite 5 + HMR)
- **UI Framework**: React 18 with TypeScript in strict mode
- **Styling & Icons**: Tailwind CSS 3.4 (dark mode via `class` strategy) + Lucide Icons
- **Embedded Database**: SQLite via `better-sqlite3` with versioned, ordered migrations
- **Local File Library**: App-managed local storage with unique UUID prefixes and relative path tracking
- **Security Boundary**: `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, restrictive Content Security Policy, and narrow typed `contextBridge` IPC
- **Packaging**: electron-builder
- **Build Environment**: Docker-based environments where required for platform-specific packaging

## Persistent Storage Layout

Persistent application data is stored in a dedicated directory beneath Electron's `userData` directory.

On a typical Linux installation:

```text
~/.config/CampusDeck/campusdeck_storage/
```

The structure is:

```text
<userData>/campusdeck_storage/
├── campusdeck.db         # Embedded SQLite database
├── library/              # App-managed local file library
└── backups/              # Scheduled SQLite snapshot backups
```

`campusdeck.db` contains the application's structured data.

`library/` contains imported documents managed by CampusDeck.

`backups/` contains database snapshot backups.

Users normally do not need to modify these files manually.

---

## Local File Library

Imported documents are stored in CampusDeck's managed local library.

The application uses unique UUID prefixes and relative path tracking to avoid filename collisions and maintain reliable references to imported files.

The library is separate from the original location of an imported file. Moving or deleting the original file elsewhere on the computer does not normally affect the copy already imported into CampusDeck.

## Backup & Restore Architecture

CampusDeck provides manual full backup and safe atomic restore directly within **Settings**.

### Backup Export

CampusDeck uses `better-sqlite3`'s native `.backup()` API to create a transactionally consistent SQLite snapshot without stopping the database.

A backup archive contains:

```text
campusdeck_backup_<timestamp>.zip
├── campusdeck.db
├── manifest.json
└── library/
```

The archive contains:

- `campusdeck.db` — complete SQLite database snapshot
- `manifest.json` — format version, schema version, creation timestamp, and SHA-256 hashes
- `library/` — managed subject documents, assignment prompts, and solution variants

The backup uses standard ZIP format and can be stored on an external drive, NAS, USB storage, another computer, or another backup location.

---

### Safe Atomic Restore Pipeline

Restore operations use a staged process designed to avoid replacing the active data with an invalid or incomplete backup.

1. **Archive Validation**  
   Verifies ZIP integrity, rejects malformed archives, enforces schema compatibility, and blocks unsafe path entries such as `../`, absolute paths, and null bytes.

2. **Staged Extraction & Checksum Verification**  
   Extracts the archive into an isolated staging directory and computes SHA-256 checksums matching those recorded in `manifest.json`.

3. **Rollback Protection**  
   The active database and library are copied into a rollback directory before replacement.

4. **Atomic Swap**  
   The active SQLite database and library are replaced with the validated backup.

5. **Database Reinitialization**  
   SQLite is reopened, pending migrations are applied if necessary, and IPC database proxies are rebound.

6. **Automatic Rollback**  
   If a failure occurs during the replacement process, the previous database and library can be restored from the rollback snapshot.

## Limitations

1. **Single Profile / Single Vault**  
   CampusDeck is designed for a single student user per operating-system user account.

2. **Local Storage Security**  
   Data and files are stored in the user's local application data directory and are **not encrypted at rest**. Full-disk encryption such as LUKS, FileVault, or BitLocker is recommended where hardware-level protection is required.

3. **Strictly Offline**  
   CampusDeck does not provide cloud synchronization or multi-device synchronization.

4. **No Built-in Remote Backup**  
   Backups are created locally. Users should copy important backups to separate storage if protection against disk failure is required.

5. **Platform Verification**  
   Linux x86_64 is currently the primary platform used for development, testing, and release verification.

## Data Recovery Guide

The built-in backup and restore system should be preferred whenever possible.

Manual recovery is available as a fallback for accidental deletion, corrupted data, or interrupted restore operations.

### Scenario A: Recovering from a Backup ZIP

Extract the backup:

```bash
unzip campusdeck_backup_<timestamp>.zip -d /tmp/recovered_campusdeck/
```

The extracted archive should contain:

```text
campusdeck.db
library/
manifest.json
```

CampusDeck should be closed before manually replacing active database or library files.

---

### Scenario B: Recovering from a Rollback Directory

If a restore operation was interrupted, check:

```text
<userData>/campusdeck_storage/
```

for directories matching:

```text
rollback_*
```

A rollback directory contains the database and library snapshot created immediately before the restore attempt.

---

### Scenario C: Direct SQLite Inspection

CampusDeck uses standard SQLite.

For example:

```bash
sqlite3 ~/.config/CampusDeck/campusdeck_storage/campusdeck.db
```

Example queries:

```sql
SELECT id, title, type, status, due_date FROM tasks;
SELECT id, name, code FROM subjects;
```

Direct modification of the database is not recommended unless you understand the schema and have a current backup.

## Database & Migration Architecture

CampusDeck uses SQLite through `better-sqlite3`.

The database schema is maintained through **versioned, ordered migrations**.

This allows the schema to evolve between application versions while preserving existing user data wherever possible.

When the application starts, required migrations can be applied automatically to bring an existing database to the current schema version.

## Security Architecture

CampusDeck follows a strict Electron security boundary.

The renderer process does not receive unrestricted Node.js or filesystem access.

Key security settings include:

```text
nodeIntegration: false
contextIsolation: true
sandbox: true
```

Privileged functionality is exposed through a narrow typed `contextBridge` IPC API.

The application also uses a restrictive Content Security Policy, including:

```text
connect-src 'none'
```

This supports the application's offline/air-gapped design by preventing normal renderer network connections.

## Privacy

CampusDeck is designed to operate without a remote backend.

Normal operation does not require:

- An online account
- Cloud storage
- A CampusDeck server
- Telemetry services
- Internet access

Academic data and imported documents remain on the local machine.

> **Important:** Local-first does not mean encrypted. The database and document library are stored as normal local files. Anyone with sufficient filesystem access may be able to access them.
